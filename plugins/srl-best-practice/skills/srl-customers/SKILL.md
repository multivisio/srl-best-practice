# Customer overlays on a shared srl design

One base design (Livingdocs components, `srl.config.json`, base `pdf.scss`/`xbrl.scss`)
serves many customers. Each customer only adds a style overlay for PDF and XBRL. For
the srl library itself (components, tokens, `srl` SCSS module, PDFreactor) use the
`srl-best-practice` skill.

## Folder layout

```
pdf/customers/nspXXX-<name>/
  custom.scss      @uses the partials in scss/ (entry point for the customer CSS)
  custom.ts        imports ./custom.scss, plus optional customer PDF scripts
  fonts/           customer font files, referenced from scss/fonts.scss
  scss/            partials: variables, colors, fonts, typography, table, cover, ...
```

- The folder name is `nsp<number>-<name>`. The build output folder is only the part
  before the first `-`: `.output/ldd/pdf/nspXXX/` and `.output/ldd/xbrl/nspXXX/`.
- Each customer has its own `build-<name>` script in `package.json`
  (`srl build --customer nspXXX-<name>`). `srl build --customer all` builds all of them.
- Adding a customer = new folder under `pdf/customers/` (copy an existing one, e.g. the
  demo customer) + a matching `build-<name>` script.

## Styling rules

1. **Override variables, not selectors.** Base component SCSS exposes tweakable values as
   CSS custom properties via `srl.system-root-style(<var-name>, <default>)`. Customers set
   those variables or the `--srl-color-*` tokens on `:root` in their partials.
2. If a customer needs a value the base does not expose yet, prefer adding a new
   `srl.system-root-style(...)` variable to the base component (with the current value as
   default) over duplicating the selector in the customer overlay. Note: that is a base
   change, so the design.zip must be uploaded too (see Deployment).
   Variable names need no `pdf`/`web` label: customer overlays only reach the PDF.
   Never rename variables customers already set (e.g. `--srl-table-background-NN`).
   Example: borders and paddings around titles per side, `--srl-title-h1-border-bottom`,
   `--srl-title-h1-padding-bottom` and so on, generated by one mixin with the defaults none / 0.
3. Customer-specific selector rules sometimes need `!important` to beat base styles.
   Keep them in the matching partial (`table.scss`, `typography.scss`, ...).
4. Fonts: declare `@font-face` in `scss/fonts.scss` with a relative `$font-path: "./fonts"`.
   Only ship the font files that are actually referenced.
5. Customer PDF scripts go in `custom.ts` (e.g. `initializeTablePageSplit` from
   `@/utils/pdf/PDFTablePageSplit` with customer options). They run on top of the base
   `pdf.js`.
6. **A customer `page:` override switches off the base page options.** Customers with a
   special page format often set their own named page on full-page components
   (`.srl-pdf-page { page: full-bleed-<customer>; }`). That rule has the same specificity as
   option classes like `.srl-hide-page-margin-boxes` and is loaded later, so the option stops
   working (page number and running headers stay visible). Give the customer a matching
   `@page full-bleed-<customer>-without-page-margin-boxes` that empties every margin box the
   base or the customer fills, and select it with
   `.srl-pdf-page.srl-hide-page-margin-boxes:not(<landscape layout classes>)`, so landscape
   layouts keep the base pages. Check the cover the same way.
7. **Inline text formats come in two shapes.** The editor's context menu writes
   `<strong class="srl-bold">` and `<em class="srl-italic">`, but keyboard shortcuts also work
   in the editor and write plain `<strong>`/`<b>`, `<em>`/`<i>` and `<u>` (no class). A base
   that styles bold with a fixed weight from `srl.$meta` and leaves `em`/`i`/`u` to the
   renderer is not changed for this without agreement; style both shapes in the customer
   overlay instead (`.srl-bold, strong, b` with a weight the bold `@font-face` really has,
   `.srl-italic, em, i`, `u`). Typography entries like `paragraph-strong` exist as
   `--srl-typo-*` variables but no base rule reads them for inline bold, so write the value
   directly. Check exports for `<strong>` without class. A family without an italic face gets
   a slanted (synthetic) italic in PDFreactor.
8. **Own page format (e.g. 210 × 280 mm).** `--srl-page-media-size` only changes the default
   `@page`. Full-page components (cover, page reference) use named full-bleed pages that are fixed
   to A4, so the customer needs its own named pages in that format (with and without margin boxes)
   and selects them on those components, landscape layouts excluded. A customer `@page` with a
   background (e.g. a coloured ToC page) is covered by the base's white `body` background inside the
   type area; set `body.pdf { background: transparent; }` in the overlay.

9. **Shared customer layer on top of the base.** When several customers share a SCSS module
   between base and overlay (a mixin that resets base defaults for a group of customers), check
   every base change against that module: does it break a rule there, and does it make a workaround
   there obsolete (then remove it and re-render the customers using it)? Comment each workaround with
   the base rule it compensates for, so it can be found again.

## Design handover

- A designer can align a customer's PDF design in a design tool when each design token there
  carries the CSS variable name of the base (e.g. as code syntax) and keeps the base value next
  to the customer value. Only the values that differ go into the overlay as `:root` variables.
- Use print values in pt; a line height in pt is valid in CSS as well.
- Aliases stay references in CSS: `var(--srl-color-primary-1000)`.
- Line heights: the base typography often uses a unitless ratio (e.g. 1.444), while a token file stores
  the base value absolute (13pt). If only the font size changes for a customer, the line height in the
  token file stays 13pt but the base scales it (8.5pt × 1.444 = 12.3pt). Whenever a font size differs,
  set the line height explicitly too, even if the token says "unchanged". Same check for any token
  whose base value in the token file differs from the real base default (compare with the built CSS).
- When the base gets new or renamed variables, the token file needs the same change.
- Check the sample layouts against the tokens before taking the values over. Typical slips: a
  font-weight token says 900 while the text layers show a lighter style (e.g. the weight's style
  is not installed and the tool kept the old one), font-weight and font-style tokens contradict each
  other, or the designer adds tokens the base does not read (e.g. spacing tokens). When asked to
  follow the layouts, the visible value wins; list every mismatch for the designer.

## Rendering a customer PDF locally

- Render with PDFreactor (e.g. the Docker image) from the customer's ns.wow PDF export plus the
  locally built `pdf.css`/`pdf.js` and the customer files in the order of
  `.output/ldd/pdf/nspXXX/pdf-configuration.xml`.
- The export is customer data. Keep it out of git (e.g. `/pdf/customers/*/pdf.html` in
  `.gitignore`), check with `git check-ignore -v` and never commit it.
- Without a licence key PDFreactor adds a watermark and an evaluation page after page 1.

## Packaging

`package-designs.mjs` (postbuild, or `npm run package-designs`) zips `.output/ldd` into
`.output/packages/`:

- `<design>-base-<version>.zip`: design.json, assets, shared fonts, base pdf/word/xbrl.
- `<design>-nspXXX-<name>-overlay-<version>.zip` per customer: design.json plus
  `pdf/nspXXX/` and `xbrl/nspXXX/`.

The version comes from `design.json`.

## Deployment (NSWOW)

- **Normally only the overlay of the customer you worked on is uploaded.** NSWOW replaces
  that customer's folder with the new upload; other customers stay untouched.
- NSWOW builds the PDF configuration dynamically from the stored standard XML plus the
  paths to the customer's CSS and JS files. A customer overlay therefore takes effect
  without touching the base.
- **The base design.zip is only uploaded when the shared project really changed**,
  whether the change needs a new version or is just a CSS fix in the core.
- When you finish a task, tell the user which ZIP(s) to upload: only the customer overlay,
  or the base design too.
