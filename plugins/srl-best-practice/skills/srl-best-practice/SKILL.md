# Simple Reporting Library (srl): best practices

Based on an analysis of `@simple-reporting/base` 1.0.53. When in doubt, read the
package source in `node_modules/@simple-reporting/base` (scripts/, scss/, srl/),
it is small and readable. The details are in the reference files:

- [references/config-and-scss.md](references/config-and-scss.md): srl.config.json, how tokens
  become SCSS mixins, functions, CSS variables and utility classes, units, media
- [references/components-and-build.md](references/components-and-build.md): component folders,
  ld-conf.json, properties, directives, validator, per-target SCSS, build commands
- [references/pdf.md](references/pdf.md): PDF target, PDFreactor script timing and
  performance, running headers, customer builds, testing

## Core rules

1. **Never edit generated files.** `.srl/`, `srl/`, `livingdocs.config.json`
   and `.srl/imports/*.scss` are regenerated by `srl prepare`,
   the Vite plugin and `srl build`. Change the sources instead: component folders,
   `ld-conf.json`, `properties.json`, `srl.config.json`, `src/assets/scss/**`.
2. **Design tokens live in `srl.config.json`**, not as literal values in SCSS.
   Use `srl.typography-<name>()`, `srl.colors-<name>()`, `srl.spacer-get(<n>)`,
   `srl.system-size-unit(<n>)` (unitless numbers only), `map.get(srl.$meta, …)`.
   Change an existing typography entry in the config instead of overriding it in SCSS.
3. **Folder number prefixes only define order.** `NNN.` is stripped for group labels
   and component names. The folder name without prefix must equal `name` in
   `ld-conf.json`, otherwise the component is not listed in its group and the
   design validator fails.
4. **One SCSS file per target** in `<component>/scss/`: `general.scss` (app, ldd,
   pdf, word, but **not** xbrl), `app.scss`, `editor.scss` (LDD), `pdf.scss`,
   `word.scss`, `xbrl.scss` (must `@use 'general';` itself). `web.scss` is not
   picked up automatically; `app.scss` and `editor.scss` include it with `@use "web";`.
5. **Branch per target with `srl.$system-build`** (`app`, `editor`, `pdf`, `word`,
   `xbrl`) when one `general.scss` needs target-specific rules.
6. **Treat build output as the source of truth.** `srl build` catches errors and
   still exits with code 0. Always scan the output for `Error`, validator messages
   and Sass `@error` text before reporting success.
7. **Pass the version for LDD builds.** `srl build --target ldd` asks for the
   Livingdocs version interactively and writes it to package.json. In scripts or
   non-interactive shells run `npx srl build <version> --target ldd`. Raise the
   version only when `livingdocs.config.json` changes in content (HTML,
   `ld-conf.json`, `properties.json`); for CSS and token changes keep the current one.
8. **An LDD build may only reorder `livingdocs.config.json`.** Compare it
   semantically (parsed JSON) with the committed version and revert pure reorders
   instead of committing noise.
9. **Nothing but folders directly in `livingdocs/`.** The group mapper deletes
   plain files at that level.
10. **Remove unused things only after checking every access path** (see
    "Checking whether a token or component is unused" below).

## Checking whether a token or component is unused

A typography entry `<name>` can be used through any of these paths. Search
`livingdocs/`, `src/`, the PDF scripts and the library's own SCSS/components:

| Path | Pattern |
|---|---|
| Mixin | `srl.typography-<name>(` |
| Getter functions | `srl.typography-get-font-size('<name>')` etc. |
| CSS variables | `var(--srl-typo-<name>-…)` in SCSS, Vue, TS or inline styles |
| Utility class | `.srl-typo-<name>` in HTML templates, `properties.json` options, Vue, exported content |
| SCSS map | `map.get(…$typography…, '<name>')` or loops over the map |
| Runtime config | `useSrlConfig()` (the whole srl.config.json is embedded into the app bundle) |

Colors follow the same pattern (`srl.colors-<name>()`, `srl.colors-get('<name>')`,
`--srl-color-<name>`, `.srl-color-<name>`, `.srl-bg-<name>`), spacers too
(`srl.spacer-get(<n>)`, `--srl-spacer-<n>`, keys in `spacer.margins.group`).

Then verify with the built output: build all targets before and after the change
and diff the CSS as selector/declaration pairs (minifiers regroup selectors, app
assets have hashed names). Only the rules of the removed token may disappear. In
built CSS, a `var(--srl-typo-<name>-…)` that appears only inside
`.srl-typo-<name>` is the auto-generated utility class, not a real usage.

## Workflow habits that paid off

- Build the affected targets after every SCSS or config change
  (`npm run build-pdf` is fast; do all targets for token changes).
- Keep the Livingdocs `ld-conf.json` name, the folder name, the BEM block class
  (`srl-<name>`) and the file name `<name>.html` identical.
- Before deleting components, grep for their classes in global SCSS
  (`src/assets/scss/*.scss`), PDF `@page` rules (`element(...)` names) and scripts.
- Commit generated `livingdocs.config.json` changes together with the component
  change that caused them.
